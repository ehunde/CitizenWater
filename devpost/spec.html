CitizenWater � Build blueprint

Technical Specification

A learning-sized plan for turning a community water issue photo into a reviewed report routed to a nearby utility, including offline capture and retry.

Approved

What this POC proves

One end-to-end report journey in a sample service area: take a photo, capture location, draft an issue description with AI, match a listed utility by distance, review and email the report, save it offline if needed, retry after reconnecting, and later mark it fixed or leave it open.

Worldwide use is the goal, but verified global utility discovery is outside this POC. The sample directory must be labeled. If no nearby match exists, show the nearest available utility as a fallback with its distance. Never invent contacts.

Architecture at a glance

The phone stores drafts/photos locally. Express protects the AI/email credentials. Utility matching is deterministic, using the sample coordinates; AI does not choose the recipient.

Report journey and recovery

  1. Capture/select photo; save draft and image blob in IndexedDB.
  2. Ask for location; save coordinates and timestamp. Explain permission needs.
  3. When online, send image to POST /api/analyze; Express returns category and editable description. If offline or AI fails, preserve draft and allow manual text/retry.
  4. Rank sample utilities by distance. Show selected utility, distance and contact. Disclose fallback and uncertain service jurisdiction.
  5. Let citizen edit, inspect recipient and image, and explicitly confirm Send.
  6. Send to POST /api/reports/email. "Submitted" means Resend accepted the request; it does not prove delivery, reading, or repair.
  7. Offline reports stay pending. Show a reminder while open and on next launch; the user initiates retry. No closed-app push.
  8. Citizen can mark fixed and archive, or keep the report open. This feedback is not external verification.

API and local data

  • POST /api/analyze accepts image data URL and coordinates; validates type/size; returns category, description and confidence note.
  • POST /api/reports/email accepts reviewed report fields, recipient and image; validates fields/size; returns submitted state and provider message ID. An ambiguous timeout becomes "status unknown."
  • GET /api/health exposes readiness only, never secrets.

Local report fields: UUID, timestamps, status (draft/pending/ready/submitted/fixed), image Blob/MIME, coordinates/location time, category/description, utility and recipient IDs, provider ID, submit/fixed times, resolution note. IndexedDB has no cross-device backup; explain local storage and provide delete action. Send location/photo only for user-requested analysis or confirmed email.

Build order

  1. Responsive screen shell, manifest, sample utility data.
  2. IndexedDB and static shell caching.
  3. Photo capture/selection and location permission/recovery.
  4. Deterministic utility matching and distance display.
  5. Express routes and editable OpenAI analysis.
  6. Review screen and Resend send result states.
  7. Pending reminder/retry and fixed/archive behavior.
  8. Full local walkthrough, then temporary HTTPS phone preview.

Out of scope and open setup choices

Deferred: worldwide verified utility directory, AI utility discovery, jurisdiction validation, call-answer detection, direct social posting, closed-app push, accounts, remote database/sync, staff dashboard, independent repair verification, maps/geocoding, store publication, production operations. A tel: link cannot confirm the call was answered; social posting requires separate APIs and permissions.

Confirm during build: sample service area/contacts, Resend sender and test recipient, OpenAI account/model availability and price, HTTPS preview host, phone/browser, photo size limit. Public launch needs abuse controls, retention policy, persistence, monitoring, and privacy/legal review.

Review checklist

  • Matches approved PRD and HTML/CSS/JavaScript/Express experience.
  • Offline save, retry, privacy and email outcomes are clear.
  • Provider acceptance is not described as utility delivery or repair.
  • Utility fallback is transparent and contacts are never invented.
  • HTTPS phone-preview requirement is clear.
